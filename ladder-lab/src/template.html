Watch one scan run.

In what order does the PLC actually do its work, and when does a button press take effect?

Before you start. A PLC is not event-driven: forever, it repeats one scan — read every input into a snapshot, solve the ladder rung by rung from that snapshot, then write every output at once. Nothing you press changes anything until the next input read.

Predict

Pause the PLC, then press START. Will the ladder show it as ON before or after you press Step Scan?

Try

Press ⏸ Pause, then Step Scan with the watch window open, and press START in between steps.

Takeaway

A PLC scan reads all inputs, solves the ladder from that one snapshot, then writes all outputs — a button press does nothing until the next input read.

Check yourself

You press START while the PLC is paused, between two scans. When does the ladder first show it as true?

Demo 9 of 17 · Part four · Stage 2

Same two rungs. Different order. Different answer.

Does it matter whether a rung comes before or after the one it depends on?

Before you start. Rungs solve top to bottom, once per scan. A rung that writes a bit hands it to later rungs in the same scan, but to earlier rungs only on the next one. Stage 1's scan order is the mechanism; this stage is what it costs you if you get the order wrong.

Predict

Load Program 6A (echo lags one scan) and 6B (echo follows the same scan) in turn. Which variant makes B_ECHO react one scan later?

Try

Place instructions from the palette to build a rung, then press ▶ Run My Program to send it to the live intersection.

Takeaway

A rung sees what an earlier rung wrote this same scan, but only sees a later rung's write on the following scan — rung order is part of a ladder program's meaning, not just its layout.

Check yourself

Program 6B has the same two rungs as 6A, just in the opposite order. Does swapping the order change what the program does?

Guidehow to use this demo

How does a real industrial controller actually think? This is a genuine scan-cycle PLC engine on the classic four-way stoplight — not an animation.

Where this sits: an Applied Engineering example project in Part four. No earlier demo is required, but if you have used Demo 2 (How a Language Model Works), the idea of a fixed, repeating computation loop should feel familiar — a PLC scan is that same idea in a control system instead of a model.

  1. Trainer. Pick a program, then press ⏸ Pause and Step Scan to watch the scan cycle one step at a time.
  2. Editor. Place instructions from the palette to build or edit a rung, then Run My Program to send it to the live intersection.
  3. Challenges. Build a program that satisfies a written spec, then press Check my program to grade it against a scripted test.
  4. Troubleshoot. Press Inject random fault, diagnose it from the intersection, then reveal to check yourself.

Getting around

The stage tabs switch stages; the live engine below them keeps running no matter which stage you are on. Details opens the mechanism, assumptions and sources for the current stage. Guide reopens this card; Settings holds Open Presenter Notes, Presentation mode, Reset, and this demo's own engine self-test.

Time

10–15 minutes to try all four stages; a full class period to work through the challenges and several troubleshoot rounds. Keyboard: Space run/pause, . step one scan.

What is live

Every number on screen is computed by the same engine, this instant

Live scan count, elapsed simulated time, image tables, ladder power-flow, intersection state

Nothing here is pre-recorded. Pressing Step Scan advances the same engine that drives free running, one scan at a time, and every readout updates from its current state.

How it works

input scan → solve rungs 0..N−1 (branches top–to–bottom) → output scan

Every input is latched into an input image table once per scan; the ladder is solved strictly top-to-bottom, left-to-right, from that one snapshot; every output is then written from the output image table, all at once. Timers and counters accumulate in simulated scan time (never the wall clock), which is what makes a run bit-for-bit reproducible at any speed.

Assumptions and simplifications

  • Scan time is fixed per your Timing setting (10–200 ms); a real controller's scan time varies with program size and load.
  • One task, no interrupts, no I/O forcing or network scan — the parts of a real controller's cycle that this teaching engine deliberately leaves out to keep one mechanism visible.

Sources

  • No external source is needed for this stage's claims — they describe this engine's own mechanism, verified by reading src/engine.js and by Settings → Run engine self-test live in the browser.
Boundary: this is a teaching engine, not a certified PLC and not an IEC 61131-3 conformance-tested runtime. It models one deterministic reading of Allen-Bradley-style ladder execution for the classroom, not any vendor's certified product.
What is live, and what is this page's own reading of a published execution model

The validator and grader run live; the AND/OR mapping is this engine's own reading of Logix-style semantics

Live validation messages and rung-order feedback

Every message the validator shows (a duplicate coil, an unused branch, a rung that writes a physical input) is computed from your program's current structure the moment you press Validate or Run.

Reasonedthis engine's own execution model, for a single controller, single scan, non-retentive OTE series = AND, parallel branches = OR, solved rung 0..N−1 in program order

This is the standard way Allen-Bradley/Logix-style ladder is taught and documented: each instruction receives a rung-condition-in and passes a rung-condition-out to the next instruction in series, so a series chain is AND and a parallel branch is OR. It is marked Reasoned rather than Sourced because the primary Rockwell instruction-set page and PDF programming manual could not be read directly in this research pass (the live page is gated behind a region/cookie interstitial that returns no instruction text, and the PDF's text layer did not decode) — the mapping is corroborated by two independent secondary references fetched the same day, not verified against Rockwell's own wording verbatim.

How it works

The editor's own palette is a deliberately constrained subset: nine instruction types, no nested branches, a fixed tag list. That constraint is this build's own teaching choice, not a limit of real ladder logic.

Assumptions and simplifications

  • The palette forbids nested branches and limits you to the tags a program declares — real Logix ladder allows both more freely.
  • The validator checks structure and tag usage (duplicate coils, writing to a physical input, an undeclared tag) — it is not a full IEC 61131-3 conformance checker.

Sources

  • Rung-Condition Behavior in Studio 5000 Ladder Logic (fetched 2026-09-16) — describes the rung-condition-in/rung-condition-out chain this stage's AND/OR mapping follows.
  • OTE (Output Energize) — OTE Definition & Explanation (fetched 2026-09-16) — OTE re-solves the tag every scan from the rung's condition.
Boundary: this stage does not claim to reproduce full Logix ladder or any specific firmware version — it teaches the series/parallel = AND/OR reading with a narrower instruction set and a stricter validator than a real programming package would enforce.
What is live

The grader runs your actual program against a scripted test, live

Live pass/attempted/not-tried status, hint reveals, grader feedback

Pressing Check my program deep-clones your program, runs it against a scripted input sequence for that challenge, and checks the outputs at each recorded step — computed here, from your program, every time you press it.

How it works

Each of the four challenges pairs a written spec and a required-tag list with a scripted sequence of inputs. The grader steps the sequence, and at each checked step compares your program's outputs against what the spec requires; the first mismatch it finds is reported with which step failed and when.

Assumptions and simplifications

  • PASSED means "matched the scripted test at every step it checked," not "is the one intended solution." A different, differently-wired program that behaves the same on that sequence passes equally well.
  • No score is kept. Hints do not cost anything and attempts are not counted, only not tried / attempted / passed.

Sources

  • No external source is needed — the grading mechanism is this demo's own, verified by reading src/challenges.js and by its own test suite (node src/challenges.test.js, 83 tests including reference solutions).
Boundary: the four challenges check one behavioral spec each. They do not grade code style, comments, or scan-time efficiency, and they are not a complete industrial-controls curriculum.

Live this engine's own "last write wins" behavior

This engine's own duplicate-OTE handling is a Live claim, not a citation: reading src/engine.js shows both coils execute every scan and the later one in program order overwrites the earlier one in the committed output image, and this is one of the 21 assertions in Settings → Run engine self-test ("Two OTE coils on the same output: both execute, last write wins in the committed image").

Reasonedfor a single controller, single scan, non-retentive OTE — as this engine models; real installations can differ real Allen-Bradley/Logix controllers behave the same way for a duplicate OTE coil

Independent PLC-programming references consistently describe "last rung solved wins" for a duplicate output coil on one controller in one scan, which is exactly the configuration this engine models. It is marked Reasoned, with a qualifier, rather than a flat Sourced claim because the research pass also surfaced public disagreement about duplicate/"destructive" outputs on other hardware and configurations (retentive instructions, distributed I/O, specific families like Micro800) — symmetric evidence in the other direction from the confident "last write always wins" framing this demo's own README used before this pass. The primary Rockwell manual could not be read directly (see Stage 2's Details for why), so this is the fetched secondary evidence, honestly labeled rather than dressed as a citation.

How it works

Each fault deep-clones the active program and changes exactly one instruction, tag, or timer preset via a structural predicate (never a hard-coded index), and every patched program is re-checked to still pass validation with zero errors before it ships. Reveal highlights the exact rungs the fault touched.

Assumptions and simplifications

  • Eleven hand-authored faults are a teaching sample, not an exhaustive fault taxonomy for real PLC maintenance.
  • Solve times are local to this browser tab, not a benchmarked or shared leaderboard.

Sources

  • Rung-Condition Behavior in Studio 5000 Ladder Logic (fetched 2026-09-16).
  • Multiple independent PLC-programming forum and reference discussions of "last rung wins" for duplicate output coils, and of documented exceptions on other configurations, fetched 2026-09-16 — named in full in .aia/.data/demo-fleet-format-alignment/B-ladder-lab-progress.md (this build's own working notes, not shipped in the page).
Boundary: this stage does not certify that every Allen-Bradley or Logix controller resolves a duplicate output coil identically in every configuration — only that this engine does, verified by its own code and self-test, and that the same behavior is well corroborated for the single-controller, non-retentive case this trainer models.
