How to use Ladder Lab

This is a real PLC, not an animation. The ladder program sits on the left, the live intersection (or motor) on the right, and every tag value underneath.

The scan cycle

The PLC never stops looping. Every lap — one scan — it does three things, strictly in this order:

  1. Reads every input into a snapshot: the input image table.
  2. Solves the rungs top-to-bottom, left-to-right, from that snapshot.
  3. Writes every output at once, from the output image table.

So pressing a button does nothing until the next input read — and a bit written by rung 5 reaches rung 6 in the same scan, but rung 4 only on the next one.

Step mode — what no physical trainer can show you

Press ⏸ Pause, then Step Scan to advance exactly one scan at a time with both image tables on screen. Rows flash when a bit changes, so you can see precisely when it changed. Keyboard: Space to run or pause, . to step one scan.

Challenges and troubleshooting

Challenges gives you four graded builds — motor seal-in, delayed start, the stoplight from a written spec, then the crosswalk. Build yours in the editor and the grader runs it against a scripted input sequence, then tells you which step failed and when.

Troubleshoot injects one of eleven faults into a working program. Diagnose it from the intersection's misbehaviour and the ladder, then reveal the explanation.

Getting started

  1. Pick a program. 5 — Motor Seal-In is the quickest way in; 1 — Basic Timed Stoplight is the full thing.
  2. Press an input on the panel — START, STOP, a pedestrian button, a car sensor — and watch the live power path light up through the ladder. Green means true.
  3. Pause and step a few scans with the watch window open.
  4. Click any instruction for a plain-English account of what it is doing right now.

Presenter's notes

Stage notes for the 45-minute lab, distilled from the teacher guide. The full printable version is under ⚙ Settings → Open teacher guide.

Run of show

  • 0–5Hook. Trainer mode, Program 1 running. Ask the room: "what is deciding when the lights change?" Introduce the PLC.
  • 5–12Scan cycle. Pause, then Step Scan with the watch window open. Press PED_NS while paused and step once — now it appears in the input image. Then Program 6 A/B for rung order.
  • 12–20Read the ladder. Program 5 (seal-in): click each instruction for its plain-English role. Then Program 1 — find the four step bits, the timers, the interlock contacts.
  • 20–32Build. Challenges 1 (seal-in) then 2 (delayed start); the auto-grader gives step-by-step feedback. Fast finishers take challenge 3.
  • 32–42Troubleshoot. Hide the ladder pane. Inject a random fault into Program 1 or 2; the class predicts the bug from the intersection alone, then reveal the ladder and confirm. Solve times make a friendly leaderboard.
  • 42–45Debrief with the questions below; assign challenge 4 as an extension.

Three things to say out loud

  • The scan cycle. Reads all inputs into a snapshot, solves the ladder top-to-bottom and left-to-right from that snapshot, writes all outputs at once. One lap = one scan; real PLCs run ~1–20 ms. A button press does nothing until the next input read.
  • Why rung order matters. A rung that writes a bit affects later rungs in the same scan, but earlier rungs only see it next scan. That one-scan difference is the root of real interlock and sequencing bugs.
  • Latch vs. seal-in. An OTE coil is re-solved every scan. A seal-in holds it on by wiring the output's own contact in parallel with START (Program 5) — lose power and the motor stays off, usually the safe choice. OTL stays on until an explicit OTU, which is why the crosswalk request in Program 2 uses one.

Misconceptions to head off

  • "Ladder is a schematic." It looks like relay wiring but it is a program, solved in order, one rung at a time. Electricity flows everywhere at once; a scan does not.
  • "Outputs change mid-rung." They update at the end of the scan, all together — watch the output image table while stepping.
  • "Pressing a button acts instantly." It acts at the next input scan. In step mode a press does nothing until you step.
  • "A timer counts wall-clock." TON accumulates only while its rung is true, in scan-time, and resets when the rung goes false.
  • "Two coils with the same tag both work." The last rung wins, every scan — see the double-coil fault.

Debrief questions

  1. Why can both directions never be green in Program 1, even if a timer misbehaves? (Two independent defenses: the step sequence and the XIO interlock contacts.)
  2. Why is the walk request latched instead of wired straight to the walk sign? What would happen if it weren't?
  3. In the Scan Order Demo, which variant would you pick for an emergency-stop rung, and why?
  4. Seal-in vs. OTL for the motor: which restarts by itself after a power blip? Which is safer, and when?
  5. Our simulated scan is 20 ms. What real-world inputs could a PLC miss entirely between scans, and how would you catch them?
